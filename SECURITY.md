# Security Policy

## Supported Versions

Security fixes ship in the latest minor release. Point releases inherit fixes
from their containing minor — i.e. the latest `0.1.x` is always patched.

| Version | Supported |
| ------- | --------- |
| 0.1.x (latest minor) | Yes |
| < 0.3.0 | No |

## Reporting a Vulnerability

Please **do not** file public issues for security bugs. Use
[GitHub Security Advisories](https://github.com/fabriziosalmi/zion/security/advisories/new)
("Report a vulnerability"). For supply-chain incidents (a published artifact
that fails [provenance verification](docs/security/supply-chain.md)) use the
same channel and tag the report as `supply-chain`.

### What to include

- A description of the vulnerability and the affected component (`src/<module>.rs`).
- Steps to reproduce, including a minimal `zion.toml` if relevant.
- A proof-of-concept request, payload, or config when possible.
- Impact assessment (information disclosure, RCE, DoS, integrity, etc.).
- Disclosure timeline you would like us to follow, if any.

### What happens next

1. Acknowledgement within **48 hours**.
2. Triage + reproduction within **5 business days**. We will share our
   severity assessment (CVSS v3.1) with you.
3. Patch development on a private branch. You can request to be added.
4. Coordinated disclosure: GHSA published, CVE assigned (when applicable),
   and a release is cut on the `master` branch with the fix.
5. Postmortem published in [docs/security/](docs/security/) for any
   high/critical-severity issue.

## Supply-chain integrity

Every Zion release carries cryptographic evidence linking it to a public
GitHub Actions build:

- **SLSA v1.0 build provenance** for every binary, the `SHA256SUMS` file,
  and every container image — generated by
  [`actions/attest-build-provenance`](https://github.com/actions/attest-build-provenance)
  and recorded in the Sigstore [Rekor](https://rekor.sigstore.dev/) public log.
- **Cosign keyless signature** for every published container image.
- **CycloneDX SBOM** attached to each release and attested to the image digest.
- **Reproducible builds** — `SOURCE_DATE_EPOCH` is wired through the build,
  archives are normalized, and the toolchain is pinned via `rust-toolchain.toml`.

Verification recipes (`gh attestation verify`, `cosign verify`,
`cosign verify-attestation`) live in
[docs/security/supply-chain.md](docs/security/supply-chain.md). If a published
release fails verification, treat it as a P0 incident — file a security
advisory immediately.

## Build-time policy gates

These checks run on every PR, daily on `master`, and on every release tag.
A release cannot be published if any of these fail:

- [`cargo audit`](https://github.com/rustsec/rustsec) — RustSec advisory DB
- [`cargo deny`](https://github.com/EmbarkStudios/cargo-deny) — advisories,
  licenses, banned crates, vendored sources (config: [deny.toml](deny.toml))
- [CodeQL](https://github.com/github/codeql) — Rust + Actions semantic SAST
- [OSSF Scorecard](https://scorecard.dev) — repo-level supply-chain posture
- `cargo clippy --all-features -D warnings` and the full test matrix

Informational signals (do not block, but are reviewed):

- [`cargo geiger`](https://github.com/rust-secure-code/cargo-geiger) —
  unsafe-surface report.
- [`cargo vet`](https://mozilla.github.io/cargo-vet/) — supply-chain trust
  audit (gated once `supply-chain/` baselines are populated).
